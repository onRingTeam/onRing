# OnRing 구현 계획서

> 기준 문서: [OnRing_화면정의서_v1.1.pdf](OnRing_화면정의서_v1.1.pdf) · [api-spec.md](api-spec.md)
> 슬로건: 언어의 장벽을 끄고, 소통의 링을 켜다.
> 이 문서는 **남은 작업을 구현 순서대로** 정리한 로드맵이다.

**기술 스택**
- 서버: Spring Boot 3.5 / Kotlin / JPA(MySQL) / Spring Security(JWT) — `backend/`
- 앱: **React Native + Expo (expo-router, TypeScript)** — `app/knou-app/`
  - 이미 포함: `expo-device`(성능 체크), `expo-router`(네비), `expo-web-browser`/`expo-linking`(소셜 로그인 콜백)
  - 추가 예정: `i18next` + `react-i18next` + `expo-localization`(앱 UI 다국어, 한/일/중/영)
- **다국어 구분(중요)**: 앱 **UI 문구**는 i18n(정적 번역 리소스), 회의 중 **발화 내용**은 런타임 번역 API(Phase 4-2). 서로 별개.

## 1. 데이터 모델 보강 (선행 작업)

## 추후에 시간남으면 추가 할것 선행작업 아님!!!

구현 ㅇ들어가기 전 스키마에 추가가 필요한 것:

- **`MessageEntity` (채팅 메시지)** — 화면 4-d(전체 대화)·5-d(채팅창)의 핵심. 현재 없음.
  - 컬럼(안): `message_id PK`, `meeting_id FK`, `sender_user_id FK`, `original_text`, `original_lang`, `spoken_at`, `created_at`
  - 번역문은 사용자 언어별로 달라지므로 **저장 전략 결정 필요**:
    - (A) 원문만 저장 + 조회/수신 시 실시간 번역
    - (B) 원문 + 언어별 번역 캐시 테이블(`message_translation`) — 재요청 비용 절감 ← 권장
- `MeetingAttendanceEntity`에 **개설자 여부(`is_host`)** 컬럼 또는 `meeting.host_user_id` 추가 — 종료 권한(5-a-1) 판단용. 현재 없음.
- 구독/잔여횟수(6-a) 를 위한 필드 — 지금은 화면만 있고 "구현 x"(6-b). 우선 `UserEntity`에 `subscribed`, `remaining_count`만 두고 정책은 보류.

## 2. 구현 순서 (서버 → 앱)

각 단계는 **서버 먼저 → 앱(클라이언트) 연동** 순. Phase 안에서도 위에서 아래로.

---

### Phase 1. 인증 / 회원 · 설정 (화면 6)

모든 화면이 "로그인된 사용자"를 전제로 하므로 **가장 먼저**.

**서버**
- [ ] 소셜 로그인 연동 (화면 6-a-ii: 소셜 로그인). 제공자 결정 필요(Google/Kakao/Apple 등)
- [ ] `AuthController` `/api/auth/**` — 소셜 인증 콜백 → 회원 조회/생성 → **JWT 발급**(`JwtTokenProvider.createToken`)
- [ ] `UserService` 구현 — `UserController` 스텁 채우기
  - `GET /api/users/me` (프로필 + 채팅설정)
  - `PATCH /api/users/me/profile` (회원명, 소셜이면 거부)
  - `PATCH /api/users/me/chat-settings` (언어/글씨크기/진동)
- [ ] 컨트롤러의 임시 `X-User-Id` 헤더 → `@AuthenticationPrincipal`(JWT subject=userId)로 교체
- [ ] 전역 예외 처리(`@RestControllerAdvice`) + 공통 에러 응답 포맷

**앱**
- [ ] **앱 UI 다국어(i18n) 기반 셋업** — `i18next`+`react-i18next`+`expo-localization`, 번역 리소스(ko/ja/zh/en) 구조, 언어 키를 서버 `Language` enum과 일치. *(이후 모든 화면 문구에 적용되는 선행 작업)*
- [ ] 내 언어 변경 시 i18n 언어 + 서버 `chat-settings.language` 동기화
- [ ] 소셜 로그인 화면 → 토큰 저장(안전 저장소) → 이후 요청 `Authorization: Bearer`
- [ ] 설정 화면(6): 프로필 카드, 채팅설정(언어 한/일/중/영·글씨크기 4단계·진동 토글)

### Phase 2. 회의 CRUD (REST) — 홈(2) · 회의록(3) · 상세(4 AI요약)

**서버** — `MeetingService` / `MeetingAttendanceService` 구현
- [ ] **회의 코드 생성기**: `날짜 + 회의명 첫글자 + UUID` (2-b-i-1)
- [ ] `POST /api/meetings` 생성 — 생성 시 개설자를 attendance에 등록, **이미 진행중 회의 있으면 409**(2-b-i-1 confirm)
- [ ] `POST /api/meetings/join` 참여 — 코드 검증: 진행중→참가 / 종료→alert / 없음→alert (2-c-i)
- [ ] `GET /api/meetings/active` 진행중 내 회의 (1-c 빨간 배경·홈 동적분기)
- [ ] `GET /api/meetings/recent` 최근 4건 (2-d)
- [ ] `GET /api/meetings` 목록/검색 — 회의명·코드·요약 like + 즐겨찾기 필터 + 페이징 (3-b·3-c·3-d)
- [ ] `PATCH /api/meetings/{id}/favorite` 즐겨찾기 토글 (3-c)
- [ ] `GET /api/meetings/{id}` 상세 AI요약 (4-b 상단카드: 참여자수·언어수·시간 / 4-c) — **요약 데이터는 Phase 4에서 채움**, 우선 구조만
- [ ] `POST /api/meetings/{id}/end` 종료 — **개설자만**(5-a-1), 종료 시 `duration_sec` 계산·`status=ENDED`

**앱**
- [ ] 홈(2): 헤더(이름), 회의시작 카드(바텀시트), 회의참여 카드(코드 입력), 최근 4건, 네비 회의탭 동적/빨간배경
- [ ] 회의록(3): 총건수, 검색, 전체/즐겨찾기 탭(클라이언트 필터), 카드 목록
- [ ] 상세회의(4) AI요약 탭 UI (데이터는 Phase 4 연동 후 채워짐)

### Phase 3. 실시간 회의 (WebSocket/STOMP) — 회의화면(5)

화면 5의 채팅은 REST가 아니라 **WebSocket(STOMP)**. (`spring-boot-starter-websocket` 이미 있음)

**서버**
- [ ] `MessageEntity`(+번역 캐시) 추가 (위 1번)
- [ ] STOMP 설정: `WebSocketConfig` (엔드포인트 `/ws`, 브로커 `/topic`, app prefix `/app`)
- [ ] 구독: `/topic/meetings/{meetingId}` (방 단위 브로드캐스트)
- [ ] 발행: `/app/meetings/{meetingId}/send` — 메시지 수신 → 저장 → **번역(Phase 4)** → 방 전체에 푸시
- [ ] 메시지 페이로드: 발화자·내용·시간·번역 (5-d)
- [ ] 참여자 입퇴장 이벤트, 종료 브로드캐스트(5-a-1 → 5-i 종료안내)
- [ ] 보안: WebSocket 핸드셰이크 시 JWT 검증(운영) / dev는 통과
- [ ] `GET /api/meetings/{id}/messages` (4-d 전체대화 조회 — 종료 후 다시보기)

**앱**
- [ ] 회의화면(5): 헤더(회의명·경과시간·종료버튼[개설자]·참여자), 채팅창, 입력/전송(enter·click)
- [ ] 내 언어 버튼(5-b): 발화/번역 언어 변경(다음 발화부터 적용)
- [ ] 마이크/스피커 음소거 토글(5-e/5-f)
- [ ] 종료 직후 화면(5-i/5-j): 종료 안내 + 홈으로

### Phase 4. 음성·번역·AI 파이프라인

회의의 실질 기능. **외부 연동 선택 필요** (각 항목 provider 결정).

**4-1. STT (음성 → 텍스트)** — 발화 입력 · **온디바이스 우선 / 서버 폴백 (하이브리드)**

요즘 폰의 기본 음성인식 성능이 충분히 좋으므로 **클라이언트 온디바이스 처리를 기본**으로 하고, 저사양 기기만 서버로 폴백한다.

- [ ] **디바이스 성능 체크** (RAM / OS 버전 등) → 임계값 기준 분기
  - `expo-device`(`Device.totalMemory`, `Device.osVersion`)로 판정
  - 임계값 **이상** → **클라이언트 온디바이스 STT** (Expo: `expo-speech-recognition` 또는 `@react-native-voice/voice` — OS 기본 엔진 사용)
  - 임계값 **이하** → 오디오를 **WAS로 전송 → 서버 STT** (폴백 경로, 현재 `/STT` 스텁 자리)
- [ ] 분기 임계값 정의(기기 등급표/RAM·OS 최소 버전) — **수치 확정 필요**
- [ ] 서버 폴백용 STT provider 결정 (예: Google/Whisper 등) — **미정** (폴백에서만 사용)
- [ ] 클라이언트는 STT 결과 **텍스트만** 서버(WebSocket)로 전송 → 서버는 번역/브로드캐스트만 담당 (온디바이스 경로에선 오디오를 서버로 안 보냄 → 트래픽·비용·지연 절감)

**4-2. 번역** — 채팅 번역(5-b·5-d), 전체대화(4-d)

핵심: **참여자별 언어 설정대로 개인화 번역**. 한 발화를 방 전체에 똑같이 뿌리는 게 아니라, **각 수신자의 내 언어(`chat-settings.language` / 5-b 내언어 버튼)로 번역해서** 보여준다. (예: 한국어 발화 → A는 영어로, B는 일본어로 수신)

- [ ] 원문 → **수신자별 언어**로 번역. 한/일/중/영 4개 (6-c-ii)
- [ ] 발화자 언어 == 수신자 언어면 번역 스킵(원문 그대로)
- [ ] 내 언어 변경(5-b)은 **다음 발화부터** 적용 (이미 받은 메시지는 그대로)
- [ ] 전송 방식 선택:
  - (A) 서버가 각 수신자 언어로 번역해 **개인 큐로 전송** (구독 시 언어 정보 활용)
  - (B) 서버는 원문+가능한 번역들을 방에 푸시, 클라이언트가 자기 언어 것만 표시
- [ ] 저장 전략: 언어별 캐시(권장, `message_translation`) vs 실시간 — 여러 수신자가 같은 언어면 캐시 재사용
- [ ] provider 결정 — **미정**

**4-3. TTS (읽어주기 모드)** — 5-c · **온디바이스 우선 / 서버 폴백 (하이브리드)**

STT와 동일 전략. 기본은 클라이언트 OS 내장 TTS로 읽어주고, 저사양만 서버 폴백.

- [ ] **디바이스 성능 체크** → 임계값 분기 (STT와 동일 기준 재사용)
  - 이상 → **클라이언트 온디바이스 TTS** (Expo: `expo-speech` — iOS `AVSpeechSynthesizer` / Android `TextToSpeech` 래핑)
  - 이하 → **서버 TTS**로 음성 합성 요청 (폴백, 현재 `/TTS` 스텁 자리)
- [ ] 서버 폴백용 TTS provider 결정 — **미정** (폴백에서만 사용)
- [ ] 이어폰 사용 권장 alert (5-c-i)

**4-4. AI 요약** — 상세회의(4-c)
- [ ] 회의 종료 시 전체 대화 → 요약 생성 (4-c-i 요약내용)
- [ ] 액션 아이템(화자별 발언 요약) (4-c-i)
- [ ] 화자별 발화빈도 집계(횟수/%) — `speech_count` 기반 (4-c-ii)
- [ ] LLM provider 결정 — 후보: **Claude API**(claude-opus-4-8 등). 별도 확정 필요
- [ ] 비동기 처리(종료 후 백그라운드) + 결과를 `meeting.summary`/`attendance.action_item`에 저장

> ⚠️ 4번은 외부 API 비용/키 관리(.env, 운영 env 주입) 동반. provider 확정 전엔 인터페이스만 정의하고 mock 구현 권장.
