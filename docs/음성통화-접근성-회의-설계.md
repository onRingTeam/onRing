# 음성통화 + 접근성 회의 설계 (WebRTC · STT · STOMP · TTS)

> 상태: **제안(Draft)** — 토폴로지 등 일부 항목은 "결정 필요"로 표시.
> 대상 화면: 회의 진행(화면 5). 관련 코드: 
`app/knou-app/src/screens/meeting-room/*`,   
`src/lib/*`, `backend/.../websocket/*`.  

## 1. 목표 / 유즈케이스

**혼합 회의**: 청인(들)은 자연스러운 실시간 **음성통화**를 하고,   
청각장애인은 **자막으로 읽고 채팅으로 발화**한다.

- 청인 ↔ 청인: 실제 목소리로 통화 (로봇 TTS 아님).  
- 말하는 사람의 음성 → **자막**으로 청각장애인에게 전달.  
- 청각장애인이 친 채팅 → 청인들에게 **음성(TTS)** 으로 들림.  

## 2. 전체 아키텍처

```
┌───────────── 청인 A ─────────────┐        ┌───────────── 청인 B ─────────────┐
│ 마이크 ─▶ WebRTC 오디오 ─────────┼───────┼───────────▶ 스피커 (자연 음성)   │
│   └─▶ 로컬 STT ─▶ 텍스트 ─┐      │        │      ┌─ 로컬 STT ─▶ 텍스트       │
│ 스피커 ◀─ TTS(수신 채팅) ─┼──────┼────────┼──────┼─▶ TTS(수신 채팅)          │
└───────────────────────────┼──────┘        └──────┼───────────────────────────┘
                            │ STOMP(텍스트)         │ STOMP(텍스트)
                            ▼                        ▼
                    ┌───────────────── 서버(STOMP broker) ─────────────────┐
                    │  /topic/meetings/{id}              (채팅/자막 텍스트) │
                    │  /topic/meetings/{id}/participants (presence)         │
                    │  /topic/meetings/{id}/signal       (WebRTC 시그널링)  │  ← 신규(Mesh 시)
                    └───────────────────────────────────────────────────────┘
                            ▲
                            │ 채팅 텍스트 수신 → 로컬 TTS 발화
                    ┌───────┴──────── 청각장애인 D ────────┐
                    │ 채팅 입력 ─▶ STOMP ─▶ (청인들 TTS)   │
                    │ 자막 표시 ◀─ STOMP (청인들 STT 텍스트)│
                    └──────────────────────────────────────┘
```

**원칙: 각자 "자기 마이크"만 STT** 한다. 남의 WebRTC 오디오를 STT하지 않는다(어렵고 부정확).

## 3. 각 기술의 역할 (병행)

| 기술 | 나르는 것 | 방향 | 비고 |
|---|---|---|---|
| **WebRTC** | 실제 마이크 오디오 | 청인 ↔ 청인 | 접근성 브릿지와 독립 |
| **STT(로컬)** | 내 마이크 → 텍스트 | 발화자 → 서버 | `SttFactory` 재사용 |
| **STOMP** | 텍스트(자막/채팅) | 전원 | 이미 구축됨 |
| **TTS(로컬)** | 수신 텍스트 → 음성 | 수신자 기기 | `expo-speech`, 본인 메시지 제외 |

> 이 파이프라인에서 **텍스트는 STOMP, 음성은 WebRTC**로 완전히 분리된다. `MeetingSocket.send()`에 WebRTC를 넣지 않는다.

## 4. WebRTC 토폴로지 결정 (음성 전용)

| | Mesh(P2P) | SFU | MCU |
|---|---|---|---|
| 클라 업링크 | N-1 | **1** | 1 |
| 서버 비용 | $0(시그널링만) | 중계 대역폭 | CPU(믹싱) |
| 통화 품질 | N↑ 시 급락 | 안정 | 안정(지연↑) |
| 적정 인원 | ~3-4 | 수십 | 다수 |

### ✅ 결정: Mesh (P2P), 최대 6인 · 오디오 전용

- **근거**: 오디오 전용이라 스트림이 가볍다(Opus ≈ 30~40kbps). 6인 기준 각 클라이언트는
  업링크 5개(≈200kbps↑) · 다운링크 5개(≈200kbps↓) + 피어 5개 — 모던 폰에서 실용 범위.
  (Mesh의 "~3-4명" 통설은 *영상* 기준이며, 오디오는 ~6인까지 무리 없음.)
- **미디어 서버 불필요.** 시그널링은 기존 STOMP 재사용, NAT 통과용 **TURN(coturn)** 만 별도 필요.
- 향후 6인 초과/영상 확장이 필요해지면 **SFU(LiveKit)** 로 전환 (모듈 factory로 교체 가능하게 설계).

## 5. 시그널링 설계

### 5-A. Mesh 선택 시 (STOMP 재사용)
새 토픽 `/topic/meetings/{id}/signal` 로 offer/answer/ICE 교환.

```jsonc
// 발행: /app/meetings/{id}/signal
{ "type": "offer|answer|candidate", "from": "sessionId", "to": "sessionId", "payload": { /* SDP or ICE */ } }
```
- presence(4장 참여자 목록)로 방의 상대 목록을 알고, 신규 입장 시 기존 참가자와 P2P 연결 수립.

### 5-B. LiveKit 선택 시
- 시그널링은 LiveKit이 담당. 백엔드는 **입장 토큰(JWT) 발급 엔드포인트**만 추가 (`POST /api/meetings/{id}/rtc-token`).
- 앱은 LiveKit RN SDK로 room 접속.

### 5-C. ICE 서버(STUN/TURN) 구성 — ✅ 결정
- **개발 단계**: Google 무료 STUN만 사용.
  ```
  iceServers: [{ urls: 'stun:stun.l.google.com:19302' }]
  ```
- **현재(임시): 외부 무료 TURN = Open Relay(Metered)** 사용. 가입 불필요·공개 크리덴셜.
  ```ts
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    {
      urls: [
        'turn:openrelay.metered.ca:80',
        'turn:openrelay.metered.ca:443',
        'turn:openrelay.metered.ca:443?transport=tcp',
      ],
      username: 'openrelayproject',
      credential: 'openrelayproject',
    },
  ]
  ```
- **실서비스 전환 시**: 공개 TURN은 공유·SLA 없음·레이트리밋 → **coturn 자체 호스팅**(소형 VM)으로 교체.
  Google은 STUN만 무료(TURN 미제공).

## 6. 데이터 계약 (기존 재사용)

- **자막/채팅 텍스트**: 기존 `ChatMessageRequest/Response` 그대로. (STT 결과도 이 채널로 전송)
- **TTS 트리거**: 별도 계약 불필요 — 수신한 `ChatMessageResponse`를 본인 제외 로컬 TTS.
- **presence**: 기존 `/topic/meetings/{id}/participants`.
- **WebRTC 시그널(Mesh)**: 신규 DTO 필요(위 5-A).

## 7. 클라이언트 모듈 구조

```
src/lib/
  stt/            # (기존) 마이크 → 텍스트, 플랫폼별 factory
  tts/            # (신규) 텍스트 → 음성, device(expo-speech)/server 폴백 factory
  webrtc/         # (신규) 음성통화. mesh 또는 livekit 구현 분기
  websocket.ts    # (기존) STOMP: 텍스트/presence/시그널링
```
- STT/TTS 모두 **factory 패턴**(기존 `stt.factory.ts` 컨벤션) — device 우선, 미지원/저사양 시 server 폴백.

### 조율(orchestration) 계층
`meeting-room/hooks.ts` 가 소유:
```
useMeetingSession()      # 상태/타이머 (기존)
useMeetingConnection()   # STOMP 채팅+presence (기존) + 수신 시 TTS 발화(신규)
useLocalStt()            # 마이크 → STT → socket.send() (신규)
useVoiceCall()           # WebRTC 연결/트랙 관리 (신규)
```
- "마이크 ON" 토글 → STT + WebRTC 오디오 송신 on/off.
- "음성 ON" 토글 → 수신 채팅 TTS on/off.

## 8. 백엔드 역할

- 기존: STOMP relay(채팅), presence(입장/퇴장), 회의 join/create(JPA).
- 신규(토폴로지별):
  - Mesh → 시그널링 relay 컨트롤러(`/app/meetings/{id}/signal` → `/topic/.../signal`).
  - LiveKit → RTC 토큰 발급 엔드포인트 + LiveKit 서버 SDK.
- TTS/STT **서버 폴백** 엔드포인트(기존 `TTSController`·`STTController` 확장).

## 11. 기술 부채 / 주의

- `react-native-webrtc`, `expo-speech` 는 **네이티브 모듈 → 설치 후 재빌드**(`npm run android`) 필요.
- Mesh는 TURN(coturn) 없이는 다양한 NAT 환경에서 연결 실패 가능.
- 클라 TTS 오디오를 WebRTC 송신 트랙에 주입하는 방식은 RN에서 비현실적 → **수신자 로컬 TTS**로 해결(본 설계).
